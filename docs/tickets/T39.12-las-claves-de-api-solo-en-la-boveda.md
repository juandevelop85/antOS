# T39.12 · Las Claves de API Solo en la Bóveda

> **Estado:** ⏳ Pendiente
> **Fase:** Fase 39 (Seguridad del Recinto y del Demonio)
> **Prioridad:** 🟡 Media
> **Fecha:** September 2026
> **Dependencias:** T19.2 (configuración persistente de LLM), T31.6
> (bóveda cifrada), T36.5 (`antos setup`).
> **Origen:** auditoría de seguridad de 2026-09-25.

## Descripción

`ProviderSettings` ([`llm/config.rs`](../../system/antosd/src/llm/config.rs))
tiene un campo `api_key: Option<String>` que se serializa en
`$STATE/llm.json`. `LlmConfig::save_to_state` lo escribe con
`std::fs::write`: **en claro**, con la `umask` por defecto (normalmente
`0644`) y sin escritura atómica — lo contrario de lo que T31.6 estableció
con `crypto::write_secret_file` para todo fichero sensible.

`antos setup` ya guarda las claves en la bóveda, así que conviven dos
sitios para lo mismo, y el menos seguro es el que tiene prioridad si
alguien lo rellena a mano o una versión anterior lo escribió.

## Alcance Técnico

1. `api_key` deja de persistirse en `llm.json`: se sustituye por
   `api_key_ref: Option<String>` (nombre de la entrada en la bóveda).
2. Migración de una sola vez: si `llm.json` trae `api_key`, se mueve a la
   bóveda, se reescribe `llm.json` sin ella y se avisa.
3. `save_to_state` usa `crypto::write_secret_file` igualmente (0600,
   atómico), aunque ya no contenga secretos: la configuración decide a
   qué endpoint se envía el código del usuario.
4. Orden de resolución de claves documentado en un solo sitio: bóveda →
   variable de entorno → nada.
5. Revisar el resto de ficheros de `$STATE` que se escriben con
   `fs::write` y contienen tokens o rutas sensibles (`forge`, `web`,
   `services`).

## Criterios de Aceptación

- Test: después de configurar un proveedor con clave, `llm.json` no
  contiene la clave y tiene modo `0600`.
- Test: un `llm.json` antiguo con `api_key` se migra a la bóveda.
