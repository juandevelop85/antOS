# T33.3 · Roles antFlow Reales sobre el Runtime de Agente

> **Estado:** ⏳ Pendiente
> **Fase:** Fase 33 (Agentes que construyen software)
> **Prioridad:** 🔴 Alta
> **Fecha:** September 2026
> **Dependencias:** T33.1, T33.2, T3.1–T3.3 (antFlow, worktrees, undo por
> ticket), T1.3 (parser de tickets), T21.2 (forja: PR).
> **Origen:** Con el runtime de T33.2, los cuatro roles de antFlow pueden
> dejar de ser etiquetas y hacer el trabajo que su nombre promete, sin
> cambiar la máquina de estados ni la interfaz que ya existen.

## Descripción

`FlowEngine::run_worktree_pipeline` conserva su forma (Pending → Planning →
Implementing → Testing → Reviewing → aprobación) pero cada fase invoca un
`AgentRun` con **su modelo** (`LlmConfig::get_role_model`), **su toolset**
y **su prompt de sistema** (los `system_prompt` de los roles ya existen en
el protocolo desde T3.1):

- **Arquitecto** — entrada: ticket parseado (`spec`), `memory.search`,
  `git.status`. Toolset de solo lectura (`fs.read`, `fs.list`,
  `memory.search`). Salida: `ImplementationPlan { files_to_touch, steps,
  acceptance_checks }` (herramienta terminal tipada). Sin plan válido no
  se pasa a Coder.
- **Coder** — corre **en el worktree efímero** del ticket (T2.2), con el
  plan del Arquitecto en el prompt. Toolset de edición (`fs.read`,
  `fs.list`, `fs.patch`, `fs.write`, `test.run`). Termina con un resumen
  de cambios.
- **QA** — `test.run` real en el worktree (ya lo era); si falla, el
  **extracto del fallo** vuelve al Coder como objetivo del siguiente run
  (hasta `max_qa_retries`, ya existente). QA no edita código.
- **Auditor** — entrada: diff consolidado (`calculate_worktree_diff`),
  radio de impacto (`Blast`) y criterios del ticket. Toolset de solo
  lectura. Salida: `AuditVerdict { approve: bool, findings, risk }` —
  `audit_summary` deja de ser texto fijo. Un `approve = false` con
  hallazgos accionables realimenta al Coder; sin acción posible → Failed.
- La **aprobación humana** final (notificación + `ApproveFlow`) queda como
  está: nada se fusiona sin ella. Tras aprobar, `pr.create` (T21.2) es
  opcional.

`FlowTask.backend` pasa a `Agent` cuando el pipeline usa el runtime;
`Simulated` sigue disponible (`--simulated`) para demos y para el smoke
de CI sin modelo.

## Alcance Técnico

- **`system/antosd/src/flow.rs`:** `run_worktree_pipeline` delega cada
  fase en `agent::AgentRun` con `RoleSpec { role, model, toolset,
  system_prompt, budget }`; el `worktree_path` es el workspace del run del
  Coder/QA. Se elimina el *scaffold*. Presupuesto por rol configurable en
  `LlmConfig` (por defecto: Arquitecto 8 pasos, Coder 30, Auditor 8).
- **`system/protocolo`:** `ImplementationPlan`, `AuditVerdict`,
  `FlowTransition.report: Option<AgentReportSummary>` (pasos, coste).
- **Prompts** en `system/antosd/src/agent/prompts/` como ficheros de texto
  incluidos con `include_str!`, en español (contenido para el modelo; los
  identificadores en inglés, T31.12).
- **Autopilot (T16.3):** `generate_fix` se sustituye por un `AgentRun`
  Coder con objetivo «el build falla con: …» y presupuesto corto; si no
  hay proveedor configurado, Autopilot solo notifica (no inventa fixes).
- **CLI:** `antos agent run <ticket> --auto` usa el runtime; `--simulated`
  conserva el comportamiento anterior. `antos agent status` muestra por
  fase el modelo real, los pasos y el coste.

## Criterios de Aceptación

- Con el proveedor `fake` de T33.2 (guiones por rol), `antos agent run
  <ticket-de-prueba> --auto` en un proyecto de ejemplo: el Arquitecto
  emite un plan tipado, el Coder aplica un parche real en el worktree, QA
  pasa, el Auditor aprueba, llega la notificación de aprobación, y tras
  `ApproveFlow` el diff está en la rama del agente. Todo en `cargo test`.
- Fallo de QA en el primer intento → segundo run del Coder con el extracto
  del fallo en el objetivo (test con guion `fake` que falla y luego pasa).
- El Auditor rechaza un diff que toca ficheros fuera del plan (test).
- Ningún rol tiene `fs.patch`/`fs.write` salvo el Coder (test sobre los
  toolsets).
- `--simulated` sigue produciendo exactamente el pipeline de T33.1.
- Con clave real (opcional): un ticket pequeño real del repo termina en
  Reviewing con tests en verde.
- `cargo test --workspace` y CI en verde.
