# T31.1 · Bypass de Autenticación y Tokens Predecibles en la Consola Web Remota

> **Estado:** ✅ Completado
> **Fase:** Fase 31 (Auditoría de Código: Corrección y Endurecimiento)
> **Prioridad:** 🔴 Crítica
> **Fecha:** September 2026
> **Dependencias:** T16.4 (Consola Web Remota y Bridge WebSocket).
> **Origen:** Auditoría de código de September 2026.

## Descripción

`system/antosd/src/web.rs` levanta un servidor HTTP/WebSocket que expone estado
del sistema, tickets e incidentes del autopilot. La autenticación por token
**está escrita pero no se aplica**, y los tokens que emite **son predecibles**.
Cualquiera que alcance el puerto obtiene acceso completo de lectura.

### Defecto 1 · El resultado de la validación se descarta

En [`web.rs:431`](file:///Users/juandevelop/Develop/antOS/system/antosd/src/web.rs)
el token se valida y el resultado se asigna a una variable con guion bajo:

```rust
let _is_authed = req_token.as_deref().map(|t| Self::validate_token(state_dir, t)).unwrap_or(false);
```

`_is_authed` no se vuelve a leer en toda la función. Ninguna de las rutas
posteriores lo consulta:

- La promoción a WebSocket (`web.rs:433`).
- `GET /api/status` (`web.rs:479`).
- `GET /api/tickets` (`web.rs:492`).
- `GET /api/autopilot` (`web.rs:506`).

El guion bajo del nombre además silencia el aviso `unused_variable` de `rustc`,
que es lo que habría delatado el fallo en compilación.

### Defecto 2 · El token se deriva de un valor adivinable

`generate_token` (`web.rs:189-206`) construye la semilla como:

```rust
let seed = format!("{now}-{ttl}-{:?}", client_label);
let hash = sha1(seed.as_bytes());
```

Las tres entradas son conocidas o acotadas: `now` es el segundo Unix de
emisión, `ttl` es casi siempre el valor por defecto de 86 400, y `client_label`
suele ser el hostname o `None`. Un atacante que sepa aproximadamente cuándo se
emitió el token recorre unos pocos miles de segundos candidatos y lo reproduce
con un SHA-1 por intento. No interviene ninguna fuente de entropía del sistema.

### Defecto 3 · Superficie de exposición del token

- Se acepta en la cadena de consulta (`?token=`, `web.rs:405-414`), donde queda
  registrado en historiales de navegador, proxies y logs de acceso.
- `sessions.json` guarda el token en claro y sin restringir permisos del
  fichero, a diferencia de `vault.rs`, que sí aplica `0600`.
- No hay revocación individual ni límite de intentos.

## Alcance Técnico

1. **Aplicar la autorización.** Sustituir `_is_authed` por una comprobación real
   antes de servir cualquier ruta salvo, si se decide, un `/healthz` explícito.
   Responder `401 Unauthorized` con cabecera `WWW-Authenticate` cuando falte o
   no valide el token. Incluir la promoción a WebSocket en la comprobación.
2. **Tokens con entropía real.** Generar al menos 256 bits desde el generador
   del sistema (`/dev/urandom` vía `libc::getrandom`, o el `getentropy` de
   macOS) y codificarlos en hexadecimal o base64url. Prohibir cualquier
   derivación a partir del reloj.
3. **Almacenar solo el hash.** Guardar en `sessions.json` un digest del token
   (SHA-256 con sal por sesión), no el token en claro, y comparar en tiempo
   constante. Aplicar `0600` al fichero igual que hace `Vault::save`.
4. **Reducir la exposición.** Aceptar el token únicamente por cabecera
   `Authorization: Bearer`; retirar el parámetro de consulta o dejarlo tras una
   opción explícita documentada como insegura.
5. **Enlazar por defecto a loopback.** Verificar que `WebConsoleConfig` no
   permita `0.0.0.0` sin una confirmación explícita del usuario.

## Criterios de Aceptación

- Una petición sin token o con un token inválido a `/api/status`,
  `/api/tickets`, `/api/autopilot` y a la promoción WebSocket responde `401` y
  no filtra datos. Test de integración que lo cubra para las cuatro rutas.
- Dos llamadas consecutivas a `generate_token` con el mismo `client_label`,
  el mismo `ttl` y dentro del mismo segundo producen tokens distintos.
- `sessions.json` no contiene ningún token en claro y tiene permisos `0600`.
- Un test comprueba que un token construido desde `sha1("{now}-{ttl}-{label}")`
  ya no valida.
- `cargo test --workspace` en verde y `cargo clippy --workspace --all-targets
  -- -D warnings` sin avisos nuevos.

## Estado de Verificación (September 2026)

**Implementado** en [`system/antosd/src/web.rs`](file:///Users/juandevelop/Develop/antOS/system/antosd/src/web.rs):

1. **Autorización aplicada de verdad.** `handle_client` recibe ahora
   `auth_required: bool` (de `WebConsoleConfig::auth_required`, hilado desde
   `start` y `serve_blocking`) y comprueba el token **antes** de servir
   `/api/status`, `/api/tickets`, `/api/autopilot` y la promoción a
   WebSocket. Sin token válido, responde `401 Unauthorized` con cabecera
   `WWW-Authenticate: Bearer` (`respond_unauthorized`) y no ejecuta ninguna
   lógica de esas rutas — ni siquiera se llama a `Self::status`/`list_tickets`/
   `list_incidents`. El HTML estático de la SPA (sin datos del sistema) sigue
   sirviéndose sin token, como ya contemplaban los criterios de aceptación.
2. **Tokens con entropía real.** `generate_token` ya no deriva el token de
   `now`/`ttl`/`client_label`: genera 256 bits desde `/dev/urandom`
   (`secure_random_bytes`) y los codifica en hexadecimal
   (`ant_<64 hex chars>`). No interviene el reloj ni ningún dato adivinable.
3. **Solo se persiste el hash.** Nueva estructura interna
   `StoredSessionRecord { salt, token_hash, .. }`, distinta de
   `WebAuthSession` (que sigue devolviendo el token en claro **una sola vez**,
   al generarse). `token_hash = sha256(salt:token)` reutilizando
   `crate::pkg::crypto::sha256` (ya probado contra vectores conocidos en
   `pkg.rs`); `validate_token` compara en tiempo constante
   (`constant_time_eq`). `save_sessions` aplica `0600` al fichero, replicando
   el patrón de `Vault::save`.
4. **Exposición reducida.** Las tres rutas JSON exigen
   `Authorization: Bearer` exclusivamente. El parámetro `?token=` se
   restringió a la promoción WebSocket, documentado en el propio código como
   la única excepción viable: el constructor `WebSocket` del navegador no
   puede fijar cabeceras personalizadas en su *handshake*.
5. **Bind seguro por defecto.** `ensure_safe_bind_addr` rechaza cualquier
   `bind_addr` no-loopback salvo que se fije
   `ANTOS_WEB_ALLOW_REMOTE_BIND=1`, aplicado en `start` y `serve_blocking`
   antes de abrir el socket.

**Pruebas añadidas** (`system/antosd/src/web.rs`, módulo `tests`, 6 nuevas):
