# T35.2 · Ejecutor Confinado de Comandos de Stack y Toolchains por Proyecto vía Nix

> **Estado:** ✅ Completado
> **Fase:** Fase 35 (Proyectos por intención)
> **Prioridad:** 🔴 Alta
> **Fecha:** September 2026
> **Dependencias:** T35.1 (catálogo con `commands` y `toolchain`), T31.4
> (nada de `sh -c`; ejecución por el recinto), T7.2 (cuotas), T34.1
> (`Launcher::Nix` y la ejecución de procesos desde el ejecutor confinado),
> `env.init` (flake/devbox por proyecto).
> **Origen:** T35.1 deja un proyecto correcto pero sin `node_modules`: el
> `npm install` (o `cargo build`, `uv sync`) lo tiene que hacer alguien.
> Hoy nada en antOS ejecuta un gestor de paquetes de proyecto, y **la imagen
> de antOS Linux no trae `node`, `python3` ni `cargo`** (comprobado en
> `desktop.nix`, 2026-09-19): en la ISO ni siquiera `test.run` de un
> proyecto Node encontraría `npm`.

## Descripción

Dos cosas que son una: **ejecutar los comandos que declara un stack** sin
abrir una shell, y **tener el toolchain** con el que ejecutarlos aunque la
imagen no lo traiga.

### 1. Ejecutor de comandos de stack

Nueva capacidad `project.run` (`params`: `project` slug, `command = enum
[install, test, dev, build]`) y un `Change::StackCommand` que:

- lee `.antos/project.toml` del proyecto (T35.1) y toma el vector del
  comando pedido — **nunca** texto del usuario ni del modelo interpolado en
  una cadena; los argumentos son los del catálogo, con `{{name}}`/`{{port}}`
  sustituidos por valores ya validados como `slug`/entero;
- el programa (`argv[0]`) debe estar en la **lista blanca**: `npm`, `npx`,
  `pnpm`, `yarn`, `node`, `cargo`, `rustc`, `python3`, `uv`, `pip`, `pytest`,
  `go`, `dotnet`, `make`; cualquier otro → rechazo al cargar el catálogo,
  no en ejecución;
- corre por `sandbox::run` con `writes = $WORKSPACE/{project}/`, `scratch`
  para las cachés que los gestores escriben fuera del proyecto
  (`~/.npm/_cacache`, `~/.cargo/registry`, `~/.cache/uv`, `~/.cache/pip` —
  se redirigen **dentro** del proyecto con `npm_config_cache`,
  `CARGO_HOME`, `UV_CACHE_DIR`, `PIP_CACHE_DIR`, como `test.run` hace con
  `TMPDIR` → `target/antos-tmp`), y `network` declarada;
- `tier = "confirm"` (escribe y sale a la red); `reversible = "snapshot"`
  sobre el proyecto, excluyendo `node_modules/`/`target/`/`.venv/` del
  snapshot (artefactos, como `target/` en `test.run`);
- cuota de tiempo propia (`install`: 15 min por defecto, configurable con
  `antos quota`), salida acotada a las últimas líneas para el modelo y log
  completo en `$STATE/projects/<name>/<command>.log`.

**Honestidad sobre la red:** el recinto (`Policy.network: bool`, Seatbelt
`(deny network*)` / Landlock ABI 4) es **todo o nada**. `hosts =
["registry.npmjs.org"]` del stack aparece en el blast para que el usuario
sepa a dónde se sale, pero **no** filtra: con red permitida, el comando
puede hablar con cualquier host. Un filtro por dominio (proxy local o
reglas de red del kernel) es otro ticket; este lo documenta en la cabecera
del módulo y en el manual, y el blast lo dice con estas palabras («red:
permitida durante el comando; destino declarado: …»).

### 2. Toolchains por proyecto

El stack declara `toolchain.nix = ["nodejs_22"]`. El andamio (T35.1) ya
escribe el perfil de entorno; este ticket lo conecta:

- `project.scaffold` genera `flake.nix` y `devbox.json` **del stack**
  (reutilizando `EnvEngine::init_profile` con los paquetes del catálogo en
  vez de la lista genérica por lenguaje).
- `StackCommand` resuelve el programa en este orden: (a) binario en `PATH`
  o en los directorios habituales (`Launcher::System` de T34.1); (b) si no,
  y hay `nix`, `nix shell nixpkgs#<toolchain…> -c <programa> <args>`
  (`Launcher::Nix`, argumentos como vector); (c) si no, error que nombra
  las dos salidas (`nix` o instalar el toolchain). En antOS Linux siempre
  hay `nix`, así que la imagen no necesita engordar.
- Bajo Landlock el ejecutor no puede leer `/nix/store` (limitación conocida
  de T33.2, la misma que impide `Launcher::Nix` en `service up` desde el
  recinto): este ticket **resuelve eso** añadiendo `/nix/store` (solo
  lectura) y `~/.cache/nix` a las rutas legibles del recinto cuando el
  cambio es un `StackCommand` con `Launcher::Nix`. Si no se puede acotar
  bien, se documenta y (b) queda solo para el CLI directo — pero no se
  oculta.
- Opcional y explícito para quien lo prefiera en la imagen:
  `services.antos.desktop.toolchains = [ "node" "python" "rust" "go" ]`
  (lista vacía por defecto).

### 3. Intención

«crea un proyecto en nestjs llamado antostest» pasa a proponer **dos
pasos**: `project.scaffold` + `project.run command=install` — el blast
muestra los ficheros, la red y el tiempo estimado; una confirmación para
los dos. «instala las dependencias de antostest» / «arranca antostest» /
«prueba antostest» → `project.run` suelto.

## Alcance Técnico

- **`system/capabilities/project.run.toml`**, `exec/change.rs`
  (`StackCommand`), `exec/project.rs` (nuevo: resolución, entorno mínimo
  sin credenciales como `service/backend.rs`, redirección de cachés,
  ejecución, log), `sandbox/{seatbelt,landlock}.rs` (lecturas de
  `/nix/store` para `Launcher::Nix`), `blast.rs` (texto de red honesto),
  `planner/local` (dos pasos; verbos instala/arranca/prueba), `env.rs`
  (perfil desde el stack), `desktop.nix` (`toolchains`).
- Reutiliza `service::backend::{find_launcher-like, minimal_env}`:
  extraer a un módulo común `process/` si evita duplicar.

## Criterios de Aceptación

- En el Mac (con `node` en `PATH`): `antos -y "crea un proyecto en nestjs
  llamado antostest"` → scaffold + `npm install` dentro del recinto
  Seatbelt, `node_modules/` en el proyecto, caché de npm **dentro** del
  proyecto (nada escrito en `~/.npm`), y `antos "prueba antostest"` → test
  en verde. Blast con «red: permitida durante el comando; destino
  declarado: registry.npmjs.org».
- Test: un comando cuyo `argv[0]` no está en la lista blanca se rechaza al
  cargar el catálogo; un `{{name}}` con caracteres fuera de `slug` no llega
  a ejecutarse; ningún `sh -c` en el crate para esto (test que inspecciona
  los `Command::new` del módulo, o revisión + `grep` en CI).
- Test: sin binario y sin `nix`, `project.run` falla nombrando las dos
  salidas, sin escribir nada.
- CI Linux (job `test-linux`, que tiene `node`/`npm`): test de integración
  `#[ignore]` que hace scaffold + `install` + `test` del stack `typescript`
  base bajo Landlock. En la VM de antOS (con `nix`): el mismo flujo por
  `Launcher::Nix` para `nestjs`, anotado en el ticket.
- Snapshot del proyecto excluye `node_modules/`; `antos undo` tras el
  scaffold borra el proyecto entero (test).
- Manual y cabecera de `exec/project.rs` con la sección de red todo o nada.
- `cargo test --workspace`, clippy `-D warnings`, `fmt`; CI verde.

## Fuera de Alcance

- Filtro de red por dominio dentro del recinto.
- Servir el `dev` como servicio con puerto registrado (`env.service_up`
  para proyectos): siguiente fase si se quiere.

### 2. Lo que se decidió distinto del ticket

- `reversible = "unnecessary"`, no `"snapshot"`: con `never` el blast subía
  el plan a `grant` («hay pasos irreversibles»), y fotografiar el proyecto
  antes de un `test` habría copiado `node_modules`. Lo que se deshace es el
  andamio (`antos undo` elimina el proyecto entero, verificado); una
  instalación no es un estado que antOS deba restaurar.
- `dev` fuera del `enum`: un servidor no cabe en un paso con cuota; es
  `env.service_up` para proyectos (fase siguiente).
- El log va en `<proyecto>/.antos/logs/`, no en `$STATE/projects/`: así
  `project.run` no declara escrituras fuera del proyecto.
- El test de integración se aplica **en proceso** (`exec::apply`), no por
  `intent_session`: el ejecutor confinado relanza `current_exe()`, que en
  `cargo test` es el binario de tests (límite ya conocido de T33.2/T33.5).
  El recinto real lo ejercita CI con el binario.
