# T38.5 · El Demonio Ve las Herramientas del Sistema

> **Estado:** 🔄 En Progreso
> **Fase:** Fase 38 (Gobernanza del Workspace)
> **Prioridad:** 🔴 Alta
> **Dependencias:** T30.9 (el módulo de NixOS y sus servicios), T36.2 (la
> instalación real, donde ya apareció esta misma clase de fallo).
> **Origen:** uso real (2026-09-25). Al pedirle a la barra que creara un
> proyecto Nest, el sistema respondió: *«failed midway and reverted to
> previous state: ejecutando git init: No such file or directory (os error
> 2)»*. El undo funcionó; lo que no funcionaba era `git`.

## La causa

**NixOS sobrescribe el `PATH` de cada unidad de systemd con su lista
`path`.** `environment.systemPackages` —donde sí está `git`— no llega a
una unidad: vive en `/run/current-system/sw/bin`, que no entra en el
`PATH` del servicio a menos que se pida.

`systemd.services.antos` no declaraba `path`, así que el demonio corría
con lo que NixOS añade por defecto y nada más. Comprobado evaluando la
unidad real del sistema instalado:

```
coreutils/bin  findutils/bin  gnugrep/bin  gnused/bin  systemd/bin  (+ sbin)
```

Ni `git`, ni `node`, ni `cargo`, ni nada. Y como el demonio es quien
ejecuta las capacidades, **todo lo que se apoye en un binario externo
fallaba con `os error 2`**: `git init` al crear un proyecto, el estado de
git que pinta la barra, y `npm`/`npx` para un proyecto Nest.

Es la misma clase de fallo que tumbó el primer smoke de instalación, donde
`nixos-install` murió con «nix: command not found» (T36.2). Aquella vez se
arregló un servicio; este quedó igual.

## Alcance Técnico

- `systemd.services.antos` declara su `path`: `git`, `openssh` (git sobre
  ssh), `bash`, `coreutils`, `findutils`, `gnugrep`, `gnused`, `gawk`,
  `gnutar`, `gzip`, `nix` y **`/run/current-system/sw`** al final.
  - El perfil del sistema es la parte importante: ahí están las
    herramientas del desarrollador (node, cargo, python…) que
    `antos project init` necesita según el stack. Va el último para que
    los paquetes fijados manden sobre lo que se instale encima.
- `systemd.services.antos-doctor` recibe `/run/current-system/sw`: sondea
  con binarios externos (`flatpak`) y sin el perfil informaba «no
  detectado» de cosas que sí están instaladas.

## Criterios de Aceptación

- El `PATH` de `antos.service` contiene `git` y `/run/current-system/sw`
  (comprobable con `nix eval` sobre la unidad, sin arrancar nada).
- Crear un proyecto desde la barra completa el `git init`.
- El badge de git de la barra muestra estado real en un repositorio.
- Una capacidad que necesite una herramienta ausente falla diciendo **qué
  falta**, no con un `os error 2` desnudo.

## Fuera de Alcance

- Empaquetar toolchains concretos en la imagen (node, cargo, python): eso
  lo decide quien instala, y el perfil del sistema es el camino.
- Revisar el resto de servicios del módulo uno por uno; si aparece otro
  con el mismo síntoma, se añade aquí.

## Estado de Verificación (2026-09-25)

- `nix eval` sobre `systemd.services.antos.environment.PATH` del sistema
  instalado **antes**: los cinco paquetes por defecto, sin `git`.
  **Después**: `git-2.55.0/bin`, `openssh-10.5p1/bin`, `nix-2.34.8/bin` y
  `/run/current-system/sw/bin`. Es una comprobación sobre la unidad que se
  instala, no sobre la intención del código.
- **Pendiente**: crear un proyecto desde la barra en el sistema instalado
  y ver el `git init` completarse. Eso exige reconstruir la ISO o un
  `nixos-rebuild` en la máquina, y es lo que cierra el ticket.
