# T32.3 · Servidor IPC Concurrente y Desacoplamiento de Mutación en antosd

> **Estado:** ⏳ Pendiente
> **Fase:** Fase 32 (Auditoría y Optimización de Rendimiento del Sistema)
> **Prioridad:** 🔴 Alta
> **Fecha:** September 2026
> **Dependencias:** T31.8 (límites y timeouts en IPC), T4.1 (barra de intenciones).
> **Origen:** Auditoría de rendimiento de September 2026.

## Descripción

En `system/antosd/src/ipc/transport.rs`, el bucle del servidor `serve` procesa conexiones de forma estrictamente serial:
```rust
for connection in listener.incoming() {
    let stream = match connection { ... };
    if let Err(e) = super::handle_connection(ctx, catalog, stream) {
        ...
    }
}
```
El motivo de diseño original (T31.8) era evitar que dos intenciones simultáneas mutaran el espacio de trabajo en paralelo produciendo diffs inconsistentes. Sin embargo, esto acarrea consecuencias de rendimiento y disponibilidad críticas:

### 1. Bloqueo total de clientes de solo lectura por sesiones interactivas
Cuando un cliente envía una petición `Request::Intent`, `handle_connection` desactiva el timeout de lectura (`writer.set_read_timeout(None)`) para permitir la espera de inferencia de LLM, aprobación humana de pasos o ejecución de comandos en segundo plano.
Mientras esta sesión permanece activa:
- La barra de escritorio (`antos-barra`) no puede consultar telemetría (`QueryBarraTelemetry`) ni estado de git (`QueryGitStatus`).
- Cualquier comando del CLI ejecutado en otra terminal (`antos flow list`, `antos tickets`, `antos git status`) queda completamente bloqueado o expira por timeout.
- El sistema parece colgado para cualquier otra herramienta que dependa del socket IPC.

### 2. Doble serialización JSON innecesaria
En `SocketHandler::on_result` (`transport.rs`):
```rust
fn on_result(&mut self, result: &ExecutionResult) -> Result<()> {
    let copy: ExecutionResult = serde_json::from_str(&serde_json::to_string(result)?)?;
    send(self.writer, &Event::Result(copy))
}
```
Para emitir el resultado de ejecución hacia el cliente, `antosd` serializa el struct `result` a JSON, lo parsea de nuevo a `ExecutionResult` en memoria, y acto seguido `send()` lo vuelve a convertir a JSON para escribirlo en el socket. En resultados con diffs extensos o trazas de ejecución grandes, esto triplica el trabajo de CPU y las asignaciones de memoria.

## Alcance Técnico

1. **Atención Concurrente de Conexiones IPC:**
   - Despachar cada conexión aceptada en un hilo de trabajo propio (`std::thread::spawn` o thread-pool delimitado a un número máximo de conexiones concurrentes).
2. **Cerrojo Específico de Mutación de Espacio de Trabajo:**
   - Mantener una cola o cerrojo exclusivo de mutación (`WorkspaceMutationLock` o `Mutex<Option<ActiveIntentSession>>`) que proteja **únicamente** la ejecución de `Request::Intent` o comandos que alteran el disco/worktree.
   - Peticiones de solo lectura o telemetría (`QueryGitStatus`, `ListTickets`, `GetTicket`, `QueryBarraTelemetry`, `QueryFlow`, `DiagnosePorts`, `QueryDiff`, etc.) deben ejecutarse concurrentemente sin bloquearse por intenciones en curso.
3. **Eliminación de la Doble Serialización:**
   - Modificar `SocketHandler::on_result` para evitar el ciclo `to_string` -> `from_str`. Utilizar `result.clone()` directo o transmitir la referencia serializable directamente al escritor del socket.

## Criterios de Aceptación

- [ ] Las consultas de solo lectura (`antos tickets`, `antos git status`, `QueryBarraTelemetry`) responden en menos de 50 ms aun cuando exista una sesión interactiva de `antos --intencion` esperando aprobación o ejecutando un paso.
- [ ] Múltiples clientes concurrentes pueden consultar el estado del demonio simultáneamente a través del socket Unix `antos.sock`.
- [ ] Intentar lanzar dos intenciones mutantes paralelas encolará ordenadamente la segunda hasta que finalice la primera, manteniendo la coherencia de diffs y worktrees.
- [ ] `SocketHandler::on_result` no efectúa serializaciones JSON intermedias de duplicación.
- [ ] La suite de pruebas de IPC (`cargo test -p antosd -- ipc`) pasa al 100%.
