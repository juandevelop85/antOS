# T32.5 · Consulta Unificada y Caché Consistente en el Analizador Git

> **Estado:** ⏳ Pendiente
> **Fase:** Fase 32 (Auditoría y Optimización de Rendimiento del Sistema)
> **Prioridad:** 🟡 Media
> **Fecha:** September 2026
> **Dependencias:** T1.2 (analizador git en demonio), T17.1 (aislamiento de frontera git).
> **Origen:** Auditoría de rendimiento de September 2026.

## Descripción

El analizador Git en segundo plano (`system/antosd/src/git.rs`) se encarga de proveer estado semántico al CLI, al demonio y a la barra de intenciones. El análisis de rendimiento reveló dos deficiencias sustanciales:

### 1. Multiplicidad de subprocesos Git por cada inspección
En `inspect_repo` y `get_files_and_diffs`:
Por cada llamada de análisis se lanzan hasta **cuatro procesos Git externos secuenciales**:
1. `git rev-list --left-right --count @{upstream}...HEAD` (para ahead/behind).
2. `git diff --cached --numstat` (estadísticas de líneas staged).
3. `git diff --numstat` (estadísticas de líneas unstaged).
4. `git status --porcelain=v1 -uall` (estado de ficheros).
Adicionalmente, en cada subproceso se llama a `detect_antos_root()`, que recorre directorios hacia arriba para inyectar `GIT_CEILING_DIRECTORIES`. En repositorios con árboles grandes, la sobrecarga de fork/exec de 4 binarios consecutivos eleva la latencia a cientos de milisegundos.

### 2. Inconsistencia de la caché ante modificaciones en el working tree
En `GitAnalyzer::get_status`:
```rust
let head_mtime = get_mtime(&git_dir.join("HEAD"));
let index_mtime = get_mtime(&git_dir.join("index"));

if let Some(entry) = guard.get(&repo_root) {
    if entry.head_mtime == head_mtime && entry.index_mtime == index_mtime {
        return Ok(Some(entry.status.clone()));
    }
}
```
La clave de invalidación de caché se basa exclusivamente en las marcas de tiempo (`mtime`) de `.git/HEAD` y `.git/index`.
Cuando un desarrollador modifica, añade o elimina código en su editor sin ejecutar `git add`:
- Ni `.git/HEAD` ni `.git/index` cambian de `mtime`.
- La condición de caché se cumple erróneamente (`true`), y el analizador devuelve un estado **obsoleto**, indicando falsamente que el repositorio está limpio o sin cambios recientes.
- Por el contrario, cuando se ejecuta `git add`, ambas marcas cambian y se disparan inmediatamente los cuatro subprocesos.

## Alcance Técnico

1. **Unificación de Consultas Git (`porcelain=v2`):**
   - Utilizar una única invocación consolidada de `git status --porcelain=v2 --branch` que proporciona en una sola salida estructurada:
     - Nombre de rama y commit actual.
     - Commits ahead/behind respecto al upstream.
     - Ficheros modificados en índice y en working tree.
     - Ficheros no rastreados (*untracked*).
   - Ejecutar `git diff --numstat` únicamente cuando se requieran métricas detalladas de líneas modificadas (+/-).
2. **Caché Fiable e Invalidación de Working Tree:**
   - Incorporar un mecanismo de comprobación ligero para el árbol de trabajo (por ejemplo, registrar el `mtime` del directorio raíz o de los subdirectorios clave de código, o invalidar ante eventos de guardado del editor/VFS).
   - Evitar cachear falsos negativos cuando haya cambios sin añadir (*dirty working tree*).
3. **Memoización del directorio raíz de antOS:**
   - Cachear el resultado de `detect_antos_root()` para no recorrer el árbol de directorios en cada llamada.

## Criterios de Aceptación

- [ ] La inspección básica de estado reduce las llamadas a subprocesos Git de 4 a 1 o 2 en el caso general.
- [ ] Modificar un archivo en el espacio de trabajo sin hacer `git add` es detectado inmediatamente por `GitAnalyzer::get_status` sin devolver datos congelados por la caché.
- [ ] `detect_antos_root()` se resuelve en $O(1)$ tras la primera invocación mediante inicialización estática o memoización.
- [ ] Las pruebas unitarias de `git::tests` pasan al 100% conservando el aislamiento de frontera (`GIT_CEILING_DIRECTORIES`).
