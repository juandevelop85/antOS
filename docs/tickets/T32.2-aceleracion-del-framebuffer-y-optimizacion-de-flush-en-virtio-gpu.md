# T32.2 · Aceleración del Framebuffer y Optimización de Flush en VirtIO GPU

> **Estado:** ⏳ Pendiente
> **Fase:** Fase 32 (Auditoría y Optimización de Rendimiento del Sistema)
> **Prioridad:** 🔴 Alta
> **Fecha:** September 2026
> **Dependencias:** T23.3 (consola gráfica framebuffer), T18.2 (consola aarch64).
> **Origen:** Auditoría de rendimiento de September 2026.

## Descripción

El subsistema de consola gráfica y compositor 2D del kernel interactúa directamente con el framebuffer lineal. Se identificaron tres problemas de rendimiento severos en el trazado de gráficos:

### 1. Renderizado píxel a píxel a memoria VRAM sin ráfaga
En `kernel/src/console/framebuffer.rs`:
- `Framebuffer::draw_char` recorre los 128 píxeles de cada glifo bitmap llamando individualmente a `put_pixel`:
  ```rust
  for col_idx in 0..FONT_WIDTH {
      let px = x + col_idx;
      let is_fg = (row_byte & (0x80 >> col_idx)) != 0;
      let color = if is_fg { fg } else { bg };
      self.put_pixel(px, py, color);
  }
  ```
- Cada `put_pixel` comprueba límites horizontal y vertical, multiplica `(y * stride + x) * bytes_per_pixel` y efectúa escrituras de 8/32 bits sobre memoria no cacheada (PCI BAR/MMIO).
- `Framebuffer::draw_rect` repite el mismo patrón de doble bucle invocando `put_pixel` individualmente, en vez de transferir filas contiguas.

### 2. Flushes masivos e incondicionales de pantalla en AArch64
En `kernel/src/console/mod.rs` (`Console::newline`):
```rust
#[cfg(target_arch = "aarch64")]
crate::arch::aarch64::virtio_gpu::flush_screen(
    0,
    0,
    self.framebuffer.width(),
    self.framebuffer.height(),
);
```
En cada carácter de nueva línea (`\n`), el kernel envía dos comandos VirtIO completos (`CmdTransfer2d` y `CmdFlush`) transfiriendo los $1024 \times 768 \times 4$ bytes (3 MiB) de la pantalla entera. Cada comando realiza un bucle de espera activa de hasta 2.000.000 de ciclos (`exec_cmd`). Escribir un volcado de arranque de 60 líneas genera 120 transferencias completas de VRAM y congela la CPU durante segundos.

### 3. Limpieza ineficiente en `Surface::clear`
En `kernel/src/ui/surface.rs`:
```rust
pub fn clear(&mut self, color: Color) {
    let pixel = color.to_u32_argb();
    let total = (self.width * self.height) as usize;
    unsafe {
        for i in 0..total {
            *self.buffer.add(i) = pixel;
        }
    }
}
```
En pantallas 1080p, recorre 2.073.600 iteraciones con punteros escalonados en lugar de utilizar `core::slice::fill` o instrucciones vectorizadas de CPU.

## Alcance Técnico

1. **Blitting por fila y palabras completas en `Framebuffer`:**
   - Implementar `draw_glyph_row` o escritura por palabra de 32 bits en `draw_char`, precalculando el puntero inicial de la fila (`y * stride + x`) una única vez por fila del glifo en vez de 128 veces por carácter.
   - Optimizar `draw_rect` para rellenar líneas horizontales completas (`memset` / `core::slice::fill`) cuando el framebuffer sea empaquetado de 32 bits.
2. **Seguimiento de Regiones Dañadas (*Dirty Rectangles*) en Consola:**
   - Modificar `Console` para registrar el área mínima modificada (`dirty_min_y`, `dirty_max_y`).
   - En `newline`, desplazar únicamente la región que scrollea y transferir por VirtIO GPU sólo la banda rectangular afectada (la nueva línea o el área de desplazamiento), eliminando el flush de la pantalla completa.
3. **Optimización de `Surface::clear`:**
   - Reemplazar el bucle manual `for i in 0..total` por `core::slice::from_raw_parts_mut(self.buffer, total).fill(pixel)`.

## Criterios de Aceptación

- [ ] `draw_char` realiza un único cálculo de dirección base por fila de glifo, reduciendo las operaciones de direccionamiento de 128 a 16 por carácter.
- [ ] `draw_rect` utiliza llenado de memoria contiguo por fila sin llamar a `put_pixel`.
- [ ] En AArch64, `virtio_gpu::flush_screen` en `Console::newline` se limita a la región vertical dañada en lugar de transferir la resolución completa ($W \times H$).
- [ ] `Surface::clear` emplea `slice::fill`, reduciendo drásticamente los ciclos de reloj de borrado de búfer.
- [ ] La consola y el compositor de escritorio mantienen fidelidad gráfica idéntica en QEMU x86_64 y AArch64.
