# T28.7 · Paridad de Display: virtio-gpu-pci, ramfb y Cadena de Fallback de Framebuffer

> **Estado:** ✅ Completado
> **Fase:** Fase 28 (Periféricos Completos y Robustez de Plataforma Bare-Metal)
> **Fecha:** September 2026
> **Dependencias:** **T28.2** (bus PCIe) para `virtio-gpu-pci`. El resto es independiente.

## Descripción

El descubrimiento de framebuffer en AArch64 (`kernel/src/main.rs`) solo cubre: GOP de Limine (ruta UEFI), nodo DTB `simple-framebuffer`, y escaneo **MMIO** de VirtIO-GPU. Bajo QEMU `-M virt` con arranque directo (`-kernel`) ninguna de las tres se cumple de forma fiable y la ventana queda **negra**, aunque el kernel esté vivo por serie. Falta soporte de **virtio-gpu-pci** y de **ramfb** (fw_cfg), que son las formas más habituales de tener pantalla en QEMU/UTM sin UEFI.

Este ticket lleva el descubrimiento de display a paridad con el de entrada: varias fuentes, cadena de *fallback* ordenada y un log que explica qué se usó y por qué.

## Alcance Técnico

1. **VirtIO-GPU sobre PCIe (`kernel/src/arch/aarch64/virtio_gpu.rs` + `virtio_gpu_pci.rs` nuevo, o extensión):**
   - Detectar `virtio-gpu-pci` (`vendor 0x1AF4`, `device 0x1050`) en `scan_pci_bus` (requiere **T28.2**).
   - Transporte VirtIO **moderno** sobre PCIe: *capabilities* `VIRTIO_PCI_CAP_COMMON_CFG` / `NOTIFY_CFG` / `ISR_CFG` / `DEVICE_CFG`, localizadas por BAR + offset.
   - Reutilizar la lógica de comandos 2D existente (`RESOURCE_CREATE_2D`, `SET_SCANOUT`, `TRANSFER_TO_HOST_2D`, `RESOURCE_FLUSH`).

2. **ramfb / fw_cfg (`kernel/src/arch/aarch64/fw_cfg.rs`, nuevo):**
   - Driver fw_cfg MMIO (`-M virt`: registros en `0x0902_0000`), interfaz DMA.
   - Buscar el fichero `etc/ramfb` en el directorio fw_cfg; escribir `struct RAMFBCfg` (`addr` big-endian, `fourcc`, `flags`, `width`, `height`, `stride`) apuntando a un framebuffer lineal reservado en RAM del kernel.
   - Exponerlo a `console::init_raw` como framebuffer directo.

3. **Cadena de *fallback* (`kernel/src/main.rs`, `kmain_arm64`):**
   - Orden: **GOP Limine → DTB `simple-framebuffer` → VirtIO-GPU MMIO → VirtIO-GPU PCIe → ramfb → headless (solo serie)**.
   - Log explícito de la fuente elegida y del motivo de fallo de las anteriores.

4. **DTB (`kernel/src/arch/aarch64/dtb.rs`):**
   - Parseo correcto del nodo `framebuffer` / `simple-framebuffer` (formato de píxel, `stride`, `reg` = addr+size) y del nodo `fw-cfg`.

## Criterios de Aceptación

- `qemu-system-aarch64 -M virt -kernel … -device virtio-gpu-pci -display cocoa`: el Desktop Shell se pinta (hoy negro).
- `qemu-system-aarch64 -M virt -kernel … -device ramfb -display cocoa`: el Desktop Shell se pinta.
- UTM Método B (imagen UEFI) sigue pintando por GOP de Limine, sin regresión.
- El log de arranque lista la cadena de *fallback* intentada y la fuente final de framebuffer.
- `crate::console::resolution()` devuelve la resolución real en los tres caminos (MMIO, PCIe, ramfb).
- Pruebas unitarias del parser de *capabilities* VirtIO-PCI y del encoder de `RAMFBCfg` pasan con `cargo test --workspace`.

## Estado de Verificación (September 2026)

**Implementado:**

1. **VirtIO-GPU sobre PCIe** (`kernel/src/arch/aarch64/virtio_pci.rs` +
   `virtio_gpu_pci.rs`, nuevos):
   - `virtio_pci::parse_virtio_pci_cap(&[u32])` decodifica una *capability*
     vendor-specific (`cap_vndr 0x09`) → `{ cfg_type, bar, offset, length,
     notify_off_multiplier }` (puro, testeado). `discover_regions(&PciDevice)`
     recorre la lista de *capabilities*, resuelve cada región a dirección
     absoluta vía los BAR decodificados y exige COMMON+NOTIFY+DEVICE.
   - `virtio_gpu_pci::probe()` busca `1AF4:1050` / `1AF4:1010` en `scan_pci_bus`
     (T28.2). `VirtioGpuPci::init()` hace el *bring-up* moderno sobre
     `virtio_pci_common_cfg` (reset → ACK|DRIVER → `VIRTIO_F_VERSION_1` →
     FEATURES_OK → *queue* 0 con `queue_desc/driver/device` de 64 bits →
     DRIVER_OK → *notify*) y reutiliza los *packets* 2D de `virtio_gpu`
     (`RESOURCE_CREATE_2D`, `ATTACH_BACKING`, `SET_SCANOUT`, `TRANSFER_TO_HOST_2D`,
     `RESOURCE_FLUSH`). `virtio_gpu::flush_screen` ahora también refresca el
     dispositivo PCIe.

2. **ramfb / fw_cfg** (`kernel/src/arch/aarch64/fw_cfg.rs`, nuevo):
   - Driver fw_cfg MMIO + interfaz DMA (`FwCfgDmaAccess` big-endian, registro
     DMA en `base+0x10`). Verifica la firma `"QEMU"`, lee el directorio
     (`FW_CFG_FILE_DIR`), localiza `etc/ramfb` y le escribe el `struct RAMFBCfg`
     apuntando a un framebuffer lineal en `.bss`.
   - `encode_ramfb_cfg(addr, fourcc, flags, w, h, stride) -> [u8; 28]`
     (todo big-endian) y `parse_fw_cfg_file` / `find_file_selector` — puros,
     testeados. `RAMFB_FORMAT_XRGB8888 = 0x3432_5258` (QEMU lo lee con `be32()`).

3. **Cadena de fallback** (`kernel/src/main.rs`, `kmain_arm64`): orden **GOP
   Limine → DTB `simple-framebuffer` → VirtIO-GPU MMIO → virtio-gpu-pci → ramfb
   → headless**, con log por paso (fuente elegida, motivo de fallo) y una línea
   final que enumera la cadena intentada. Los tres caminos nuevos pasan por
   `console::init_raw`, así que `console::resolution()` devuelve la resolución
   real.

4. **`dtb.rs`**: `find_fw_cfg()` (nodo `qemu,fw-cfg-mmio`) y el helper genérico
   `scan_dtb_for_compatible_reg(needle)`.

**Pruebas:**
- `cargo build` del kernel para `x86_64-unknown-none` y `aarch64-unknown-none`:
  limpio.
- `cargo clippy`: x86_64 44, aarch64 45 advertencias (sin regresión).
- `cargo test --workspace` (crates host): en verde.
- Módulos `#[cfg(test)]` en `virtio_pci.rs` (4) y `fw_cfg.rs` (3) validados con un
  binario `--test` equivalente (7/7): parser de *capability* COMMON y NOTIFY
  (con `notify_off_multiplier`), rechazo de *cap* no-vendor y de entrada corta,
  `VirtioPciRegions::is_complete`; `encode_ramfb_cfg` big-endian de 28 B,
  `parse_fw_cfg_file`, `find_file_selector` sobre un blob de directorio.

**Pendiente de verificación fuera del CI headless:** arranque real en
`qemu-system-aarch64 -M virt -kernel … -device virtio-gpu-pci` y `-device ramfb`
(el Desktop Shell debe pintarse), y no-regresión de UTM Método B (GOP Limine).
El *bring-up* PCIe y el DMA de fw_cfg están implementados según la
especificación pero no se han podido ejercitar en el entorno headless; el camino
DMA de fw_cfg y las direcciones `addr_of!` como PA asumen identidad
virtual↔física en la ruta de arranque directo (misma premisa que
`virtio_gpu` MMIO).
