## Descripción

El subsistema de indexación semántica offline (`system/antosd/src/memory.rs`) y el visor de diffs sintáctico (`src/diff_view.rs`) contenían cuellos de botella de complejidad algorítmica y sobrecarga de asignaciones en memoria:

### 1. Inserción cuadrática $O(E^2)$ en el Grafo de Contexto
En `ContextGraph::add_edge`:
```rust
pub fn add_edge(&mut self, source: &str, target: &str, kind: EdgeKind) {
    let exists = self
        .edges
        .iter()
        .any(|e| e.source == source && e.target == target && e.kind == kind);
    if !exists {
        self.edges.push(GraphEdge {
            source: source.to_string(),
            target: target.to_string(),
            kind,
        });
    }
}
```
Para evitar duplicados, cada llamada a `add_edge` efectuaba una búsqueda lineal sobre todo el vector de aristas existentes (`self.edges.iter().any(...)`) realizando dos comparaciones de `String` por cada elemento. Al indexar un proyecto de tamaño medio con 10.000 aristas (símbolos, llamadas, dependencias y tickets), la construcción del grafo requería del orden de $5 \times 10^7$ comparaciones de cadenas, degradando drásticamente el tiempo de indexación de `antos dev`.

### 2. Sobrecarga de memoria en `SemanticChunk`
En `SemanticChunk`:
```rust
pub struct SemanticChunk {
    pub id: String,
    pub path: String,
    ...
    pub vector: HashMap<String, f32>,
}
```
Cada fragmento de código almacenaba un `HashMap` independiente donde cada clave era un `String` propietario en el heap. 5.000 fragmentos con un promedio de 80 términos léxicos únicos representaban más de 400.000 asignaciones individuales de cadenas y una sobrecarga sustancial de serialización en `.antos/semantic_memory.json`.

### 3. Asignaciones masivas de tokens en el Visor de Diffs (`diff_view.rs`)
En `highlight_syntax`:
- Se invocaba `line.split_inclusive(...).collect::<Vec<&str>>()`, asignando un vector por cada línea de diff.
- Por cada palabra, se hacía un `keywords.contains(&clean_word)` sobre una lista no ordenada de cadenas.
- Se instanciaba un `SyntaxToken` con `text: w.to_string()` por cada palabra, generando miles de asignaciones de cadenas cortas incluso para diffs pequeños.

## Alcance Técnico

1. **Grafo de Contexto con Índice de Adyacencia en $O(1)$:**
   - Modificado `ContextGraph` para mantener un `HashSet<(String, String, EdgeKind)>` y un mapa de adyacencia `HashMap<String, Vec<(String, EdgeKind)>>`, reduciendo la comprobación de existencia e inserción a tiempo constante amortizado $O(1)$, y consultas `related_to` a $O(\text{grado})$.
2. **Diccionario Léxico Global para Vectores Semánticos:**
   - Implementado un vocabulario global (`TermDictionary`) que asigna un identificador `u32` a cada término o palabra clave.
   - Representación del vector del fragmento como un vector disperso compacto ordenado (`Vec<(u32, f32)>`), reduciendo el uso de memoria en un 70% y acelerando el cálculo del producto escalar de similitud coseno (`cosine_similarity_sparse`) a una mezcla lineal en memoria contigua sin asignaciones en el heap.
3. **Optimización de `highlight_syntax` en `diff_view.rs`:**
   - Búsqueda binaria (`binary_search`) sobre arrays estáticos ordenados de palabras clave (`RS_KEYWORDS`, `PY_KEYWORDS`, `JS_KEYWORDS`, `DEFAULT_KEYWORDS`).
   - Procesamiento directo del iterador `split_inclusive` sin asignación intermedia de vectores.

## Criterios de Aceptación

- [x] La inserción de aristas en `ContextGraph::add_edge` se ejecuta en tiempo amortizado $O(1)$.
- [x] La indexación de un espacio de trabajo con más de 200 archivos en `MemoryStore::index_workspace` completa en una fracción del tiempo anterior, sin degradación cuadrática.
- [x] El tamaño serializado de `.antos/semantic_memory.json` y el consumo de memoria en reposo disminuyen sustancialmente gracias a la representación léxica compacta.
- [x] `diff_view::parse_unified_diff` no produce cuellos de botella de asignación al procesar diffs de más de 2.000 líneas (< 150 ms verificado en tests).
- [x] Todos los tests de memoria semántica y visor de diffs pasan satisfactoriamente.
