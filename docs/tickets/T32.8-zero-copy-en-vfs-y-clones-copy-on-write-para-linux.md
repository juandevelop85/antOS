# T32.8 · Zero-Copy en VFS y Clones Copy-on-Write en Linux

> **Estado:** ✅ Completado
> **Fase:** Fase 32 (Auditoría y Optimización de Rendimiento del Sistema)
> **Prioridad:** 🟡 Media
> **Fecha:** September 2026
> **Dependencias:** T23.4 (tarfs e initrd), T20.4 (snapshots atómicos), T20.3 (CI local paralela).
> **Origen:** Auditoría de rendimiento de September 2026.

## Descripción

La auditoría de rendimiento identificó tres puntos donde se producen copias redundantes de bytes y trabajo desaprovechado:

### 1. Duplicación de datos en el VFS del Kernel (`kernel/src/fs/vfs.rs`, `tarfs.rs`)
En `kernel/src/fs/vfs.rs`:
```rust
pub fn open(path: &str) -> Result<FileHandle, FsError> {
    ...
    let data = fs.read_file(entry)?;
    Ok(FileHandle::new(path.into(), data))
}
```
Y en `TarFs::read_file`:
```rust
TarBacking::Memory(slice) => {
    ...
    Ok(slice[start..end].to_vec())
}
```
Cuando los archivos residen en la imagen initramfs cargada en memoria (`TarBacking::Memory`), la memoria del archivo ya se encuentra disponible en un slice estático `&'static [u8]`. Sin embargo, `open` clona incondicionalmente el fichero completo al heap mediante `to_vec()`. Si un binario o un módulo del kernel inspecciona archivos de configuración o ejecutables ELF grandes, se duplican megabytes en el heap fragmentado.

### 2. Snapshots en Linux sin Copy-on-Write (`system/antosd/src/snapshot.rs`)
En `system/antosd/src/snapshot.rs`:
```rust
#[cfg(target_os = "macos")]
fn clone_tree(from: &Path, to: &Path) -> bool {
    ... // Usa clonefile(2) de APFS
}

#[cfg(not(target_os = "macos"))]
fn clone_tree(_from: &Path, _to: &Path) -> bool {
    false
}
```
En Linux (la plataforma de producción para antOS diario y NixOS), `clone_tree` devuelve siempre `false`, forzando el uso de `copy_tree`: una copia recursiva byte a byte con `std::fs::copy`. Esto hace que tomar instantáneas previas a la ejecución de agentes sea lento y consuma almacenamiento duplicado innecesariamente. En sistemas de archivos modernos en Linux (Btrfs, XFS, ZFS), el kernel soporta clonado atómico de bloques mediante `ioctl(..., FICLONE, ...)`.

### 3. Ejecución secuencial forzada en el motor de CI local (`system/antosd/src/ci.rs`)
En `system/antosd/src/ci.rs`:
A pesar de que `StageConfig` declara el atributo booleano `parallel: bool`, `CiEngine::run_pipeline` ejecuta todos los stages en un bucle secuencial simple `for stage in &config.stages`. Las fases independientes como formateo (`cargo fmt`), linteo (`cargo check`) y escaneo de secretos se ejecutan una detrás de otra en vez de aprovechar los núcleos disponibles de la CPU.

## Alcance Técnico

1. **Lectura Zero-Copy en VFS para Archivos en Memoria:**
   - Extender `FileHandle` para soportar buffers prestados (`&'static [u8]` o `Cow<'static, [u8]>`), evitando asignar vectores en el heap cuando los datos ya residen en la memoria física de `TarBacking::Memory`.
2. **Soporte de `reflink` / `FICLONE` en Linux:**
   - Implementar `clone_file_linux` utilizando la llamada `ioctl(dest_fd, FICLONE, src_fd)` para archivos regulares en Linux.
   - Si el sistema de ficheros subyacente soporta reflink / CoW, la instantánea se realiza en microsegundos sin transferir datos físicos a disco.
3. **Paralelización de Stages en CI Local:**
   - Modificar `CiEngine::run_pipeline` para agrupar los stages marcados con `parallel: true` y ejecutarlos concurrentemente mediante `std::thread::scope`, sincronizando antes de ejecutar stages secuenciales (ej. `cargo test`).

## Criterios de Aceptación

- [x] `vfs::open` no asigna memoria heap para el contenido de archivos cuando el sistema de ficheros está respaldado en `TarBacking::Memory`.
- [x] En sistemas de archivos compatibles con reflink en Linux, `snapshot::take` utiliza `FICLONE` con retorno inmediato sin copia redundante de bloques de disco.
- [x] `CiEngine::run_pipeline` ejecuta los stages paralelos concurrentemente, reduciendo el tiempo total de ejecución del pipeline local.
- [x] Los tests del workspace y las pruebas del VFS pasan al 100%.
