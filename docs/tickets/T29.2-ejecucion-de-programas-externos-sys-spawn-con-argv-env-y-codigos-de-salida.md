# T29.2 · Ejecución de Programas Externos: `SYS_SPAWN` con `argv`/`env`, `wait` y Códigos de Salida

> **Estado:** ⏳ Pendiente
> **Fase:** Fase 29 (Superficie de Comandos Soberana en el Shell Bare-Metal)
> **Fecha:** Pendiente
> **Dependencias:** T26.4 (cargador ELF64 e initramfs), T26.5 (`libantos`), T29.1 (framework de comandos).

## Descripción

El kernel ya carga y ejecuta un ELF de usuario (`antos-init` como PID 1, T26.4/
T26.5) y expone `SYS_SPAWN` / `SYS_WAITPID` (T22.5/T23.5). Pero el shell **no
usa** esa ruta: no puede ejecutar `/bin/foo`, no pasa `argv`, y `SYS_WAITPID` no
devuelve el código de salida del hijo de forma utilizable.

Este ticket cierra el ciclo: `SYS_SPAWN` acepta un vector `argv` (y `env`
opcional), `SYS_WAITPID` devuelve el código de salida, y el shell resuelve
`comando args…` contra `/bin` y `/sbin` del VFS, lo lanza, espera y propaga el
código. Es el requisito para las coreutils soberanas de T29.3.

## Alcance Técnico

1. **ABI del kernel (`kernel/src/syscall/`):**
   - `SYS_SPAWN` pasa a recibir: `ptr_path`, `len_path`, `ptr_argv`, `argc`
     (`argv` = array de `(ptr, len)` en memoria de usuario), y opcional
     `ptr_envp`, `envc`. Compatibilidad: `argc == 0` equivale al comportamiento
     actual.
   - El kernel copia `argv`/`env` a memoria del kernel, valida punteros de
     usuario (rango, longitud máxima por argumento y total), y los deja en la
     pila inicial del proceso hijo según el contrato ABI de `libantos`
     (`argc`, `argv[]`, `NULL`, `envp[]`, `NULL`).
   - `SYS_WAITPID` devuelve `Ok(exit_code_i32)` del hijo (o error si el PID no
     existe / no es hijo). Sin `unwrap`/`expect` en esta ruta.
   - Documentar el nuevo contrato en el módulo de syscalls y en
     `user/libantos/src/syscall.rs`.

2. **Recolección de la tabla ABI:** actualizar la tabla de syscalls de
   `docs/manual-de-comandos.md` §E con la nueva firma de `SYS_SPAWN`.

3. **`libantos` (`user/libantos`):**
   - `fn spawn(path: &str, args: &[&str]) -> Result<Pid, SpawnError>`.
   - `fn wait(pid: Pid) -> Result<i32, WaitError>`.
   - `fn run(path: &str, args: &[&str]) -> Result<i32, SpawnError>` (spawn +
     wait), usado por el shell.
   - Lectura de `argc`/`argv` en el `_start` del runtime de usuario para que
     los binarios reciban sus argumentos.

4. **Shell (`user/src/main.rs` + `shell::registry` de T29.1):**
   - Resolución tipo `PATH`: si el nombre no es un *builtin*, buscar
     `/bin/<nombre>` y luego `/sbin/<nombre>` en el VFS; si existe y es ELF,
     `libantos::run(path, argv)`.
   - Propagar el código de salida a `$?` del `ShellContext`.
   - Errores claros: `comando no encontrado`, `no es un ejecutable`,
     `fallo al lanzar el proceso` (todos con código de salida distinto).

5. **Un binario de prueba** (`user/examples/hello` o similar, `no_std`) que
   imprime sus argumentos, empaquetado en el initramfs por `builder`, para el
   test de humo.

## Criterios de Aceptación

- Desde `antos>`, `hello uno dos` lanza `/bin/hello`, que imprime
  `argv = [hello, uno, dos]`, y el shell recupera su código de salida.
- `hello` que sale con código 3 deja `$? = 3` en el shell (visible en T29.3 vía
  `echo $?`).
- Un nombre inexistente → `comando no encontrado` y `$? = 127`; un fichero no
  ELF en `/bin` → `no es un ejecutable` y código ≠ 0; ningún caso entra en
  pánico.
- `SYS_SPAWN` con `argc == 0` sigue funcionando igual que antes (sin
  regresión de PID 1).
- Tests: *round-trip* de codificación/decodificación de `argv` (ptr/len ↔
  `Vec<String>`) y de la resolución de rutas `/bin`→`/sbin` como pruebas puras.
- `system/run-arm.sh --test` (o `--test-input`) incluye un paso que ejecuta
  `hello a b` por la serie y verifica el eco de los argumentos.
- `cargo check --workspace`, `cargo build` del kernel (ambos targets) y
  `cargo clippy` sin regresión.
